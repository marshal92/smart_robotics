Отдельно двигать звенья руки по TF поверх этой иерархии не будем: это дублировало бы преобразования.
Текущий теневой робот остаётся самостоятельной визуализацией с собственным источником позы. Его положение не должно перезаписывать положение основного робота.

    • цвета и освещение;
    • корректность выбора точки мышью.
Старые импорты загрузчиков и использование window.THREE заменяем обычными модульными импортами.

    2. Возвращать отсутствие результата, если цепочка до fixedFrame не собрана.
    3. Обнаруживать циклы по посещённым кадрам.
    4. Не выдавать неполную позу за положение относительно map.
    5. Проверить получение /tf_static при открытии страницы после запуска робота.
    6. При переподключении очищать устаревшее состояние и корректно восстанавливать получение данных.
Если глобальная поза недоступна, интерфейс должен это обозначать. Для проверки геометрии остаётся режим осмотра модели относительно её основания.
Шаг 6 — привести в порядок жизненный цикл.
При закрытии компонента должны удаляться:
    • ROS-подписки сцены;
    • обработчики событий;
    • ResizeObserver;
    • цикл отрисовки;
    • controls, текстуры, геометрии и материалы.
При переподключении нельзя создавать вторую сцену, второй цикл отрисовки или повторные подписки. Это особенно важно после обсуждённой проблемы с ресурсоёмкостью.
Шаг 7 — проверить и завершить миграцию.
Первый этап считаем выполненным, когда:

    • корпус получает одну корректную позу;
    • отсутствие TF отображается явно;
    • переподключение не умножает подписки;
    • повторное открытие компонента не вызывает накопления ресурсов;
    • в используемой 3D-части одна версия Three.js и нет ROS3D;
    • внешний вид проверен рядом с контрольным, включая ранее исправленную проблему «дымки».

Шаг 2. Заменить ROS3D.Viewer на свой небольшой модуль
Сейчас этот блок:
viewer = new ROS3D.Viewer({
  divID: 'viewer3d',
  width: initWidth,
  height: initHeight,

Модуль должен предоставлять такой интерфейс:
const viewer = createViewer(container, {

viewer.renderer

В нём не должно быть ROS-подписок, URDF, карты или модели робота. Только техническая основа отображения.

Ключевая часть создания:
import * as THREE from 'three'
import { OrbitControls } from 'three/addons/controls/OrbitControls.js'

const scene = new THREE.Scene()

const camera = new THREE.PerspectiveCamera(
  45,    // угол обзора
  1,     // aspect будет установлен при resize
  0.01,  // ближняя граница: можно приблизиться к руке
  200
)

camera.up.set(0, 0, 1)
camera.position.set(3, -4, 3)

const renderer = new THREE.WebGLRenderer({
  antialias: true,
  alpha: false
})

renderer.setClearColor(0x111111, 1)
renderer.setPixelRatio(Math.min(window.devicePixelRatio, 1.5))
renderer.outputColorSpace = THREE.SRGBColorSpace
renderer.toneMapping = THREE.NoToneMapping

container.appendChild(renderer.domElement)

const controls = new OrbitControls(camera, renderer.domElement)
controls.target.set(0, 0, 0.3)
controls.enableDamping = true
controls.update()
Значения камеры здесь стартовые, не параметры кинематики робота.
alpha: false задаёт непрозрачный canvas непосредственно при создании renderer. Старые CSS-приёмы с translateZ(0) и will-change после этого проверяем на необходимость, а не автоматически переносим как обязательное условие.
Ограничение pixel ratio уменьшает нагрузку на экран высокого разрешения. Позже можно сделать выбор качества в настройках.
Цветовое пространство задаём осознанно: в современном Three.js обработка цветов отличается от старой версии. Копирование прежних настроек материалов без проверки может изменить яркость изображения. threejs.org
Что удалить из DigitalTwin3D.vue после переноса
    • import * as ROS3D from 'ros3d';
    • создание ROS3D.Viewer;
    • старый код настройки света внутри viewer;
    • старый ResizeObserver, если resize уже принадлежит новому модулю;
    • window.THREE = ...;
    • любые дополнительные циклы отрисовки.
Затем создание сцены сводится к:

  background: isLight ? 0x555555 : 0x111111

Остальные обращения вида viewer.scene.add(...) и viewer.camera можно сохранить на время миграции. Так не придётся одновременно переписывать весь компонент.
Проверка шага 2: без ROS отображаются оси и сетка, камера вращается, масштабируется, fullscreen и изменение размера окна работают.

Шаг 3. Отделить создание сцены от подключения к ROS
Сейчас у тебя initViewer() вызывается только при store.isConnected. Это связывает две независимые вещи.
Нужное поведение:
Событие
Действие
Vue-компонент появился
Создать viewer и пустые слои
ROS подключился
Подключить получение данных
ROS отключился
Отметить данные как недоступные; сохранить сцену
ROS переподключился
Восстановить получение данных без второй сцены

В DigitalTwin3D.vue остаются три операции:
createScene()
connectSceneData()
destroyScene()
Это названия будущих функций, которые нужно реализовать, а не добавить поверх старого initViewer().
Сцену не пересоздаём при каждом reconnect. Иначе будут теряться положение камеры и пользовательские настройки, а при ошибках очистки — накапливаться подписки.
При этом учитываем поведение установленного roslib: если его подписки сами восстанавливаются после reconnect, не создаём второй комплект вручную. Управление подписками должно находиться в одном месте.

Шаг 4. Вернуть текущий корпус и проверить координаты
Сначала переносим существующий STL корпуса. Это контрольный объект: его внешний вид уже знаком, поэтому проще заметить ошибку миграции.
Старую загрузку:
import('three/examples/js/loaders/STLLoader.js')
new window.THREE.STLLoader()
заменяем на:
import { STLLoader } from 'three/addons/loaders/STLLoader.js'

const loader = new STLLoader()
URL корпуса на этом шаге можно оставить существующий. Перестройку HTTP-путей делаем при подключении URDF.
Структура объектов должна быть такой:
const robotPose = new THREE.Group()
const robotMesh = new THREE.Mesh(geometry, material)

robotMesh.scale.setScalar(0.001)

robotPose.add(robotMesh)
viewer.scene.add(robotPose)
Здесь:
    • robotPose — положение и ориентация корпуса в метрах;
    • robotMesh — только геометрия STL и её масштаб;
    • TF изменяет robotPose;
    • коэффициент 0.001 относится только к этому STL.
Не масштабируем robotPose, иначе будущие смещения дочерних объектов тоже уменьшатся.
Для проверки сначала используем спокойный материал:
const material = new THREE.MeshStandardMaterial({
  color: 0x1976d2,
  roughness: 0.65,
  metalness: 0.15
})
Глянец, дополнительные отражения и тени настраиваем после проверки геометрии. Старое самосвечение корпуса нельзя переносить как средство исправления общей яркости сцены.
Проверка: размер корпуса соответствует метровой сетке, модель стоит правильно, камера позволяет осмотреть её вблизи.

Шаг 5. Исправить TF и подключить движение корпуса
Для текущего корпуса выбираем один соответствующий ему кадр. Сейчас два callback перезаписывают положение одного объекта:
tfClient.subscribe('base_link', updateRobotPose)
tfClient.subscribe('base_footprint', updateRobotPose)
После проверки привязки STL оставляем один. Для будущей полной URDF-модели будем использовать её действительный корневой link.
В TF-хранилище нужны следующие правила:
Ситуация
Результат
Цепочка до нужного кадра собрана
Вернуть преобразование
Нет родительского преобразования
Вернуть null
Обнаружен цикл
Вернуть null и диагностировать ошибку
Получен некорректный quaternion
Не применять его к объекту
Пришёл новый TF
Обновить данные, не создавать новую геометрию
Критическая замена в текущем алгоритме:
if (!node) {
  return null
}
вместо break с последующей выдачей частичной позы.
Для обнаружения циклов нужен Set посещённых кадров, а не только ограничение «20 переходов».
При отсутствии TF сохраняем последнюю допустимую позу и обозначаем, что она не обновляется. Не отправляем робота в ноль, поскольку это будет выглядеть как реальное перемещение.
Также разделяем:
    • доступность ROS-соединения;
    • полноту TF-цепочки;
    • свежесть данных.
Старый timestamp у фиксированного крепления из /tf_static сам по себе не означает потерю связи. Для манипулятора позднее отдельно контролируем получение его состояний: агрегатор /joint_states может продолжать публиковать сохранённые значения.
Проверка: корпус движется без скачков между двумя кадрами, а отсутствие части TF не создаёт ложной позиции.

Шаг 7. Перенести постановку навигационной цели
Здесь в твоём коде есть отдельная деталь: toggleNavMode() сейчас лишь меняет флаг. События мыши пытаются подавить управление камерой через stopPropagation().
В новой реализации лучше явно переключать режим:
function setNavigationMode(enabled) {
  isNavMode.value = enabled
  viewer.controls.enabled = !enabled
}
Порядок работы:
    1. В обычном режиме мышь управляет камерой.
    2. В режиме постановки цели управление камерой отключено.
    3. Нажатие на карту задаёт начало.
    4. Перетаскивание задаёт направление.
    5. Отпускание публикует цель.
    6. Завершение, отмена или pointercancel возвращают управление камерой.
Для мыши и сенсорного экрана используем единые Pointer Events, чтобы не поддерживать две расходящиеся реализации.
Есть и важная проверка координат: Raycaster возвращает точку в координатах сцены. Её можно публиковать с frame_id: 'map' только если сцена действительно сейчас в map. В режиме осмотра модели отправка навигационной цели должна быть недоступна.
Проверка: камера не вращается одновременно с выбором цели, стрелка соответствует отправленной ориентации.
